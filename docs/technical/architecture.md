# Architecture

Last updated: 2026-10-30

## Overview

Platform for analyzing Spanish IIC (Collective Investment Schemes) to produce a fund panorama, a candidate watchlist (≤ 20 compartments), and a flow/fee/quality layer. Analytical signals, not recommendations. The same repo supports a Deals/Financial Analytics narrative and a Data Engineer narrative.

## Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Parsing | PySpark | XML parsing, nested structure flattening |
| Local storage | DuckDB | Analytical database, advanced SQL support |
| Cloud storage | ADLS Gen2 | Bronze/Silver/Gold files in Azure |
| Local transformation | dbt-duckdb | SQL models, tests, documentation |
| Cloud warehouse | Azure SQL Database serverless | Gold serving layer |
| Cloud transformation | dbt-sqlserver | Same models against Azure SQL |
| Orchestration | Airflow on Azure VM + Docker Compose | Scheduling, dependencies, retries, backfills |
| IaC | Bicep | Storage, SQL, VM, Key Vault, budget |
| CI/CD | GitHub Actions + OIDC | Lint, tests, dbt build, Docker build |
| Secrets | Key Vault + managed identity | No long-lived credentials |
| BI | Power BI | Executive Summary + Anomaly/Forensic tabs |
| Exploration | Jupyter | Interactive analysis and validation |

## Data Layers

### Bronze (raw)
- Original ZIP files from CNMV (FONDMENS + FONDREGISTRO monthly; FONDTRIM + FONDCART semiannual, FONDPATRIMDISVAR quarterly) and ECB €STR CSVs
- Location: `data/raw/` (zips) and `data/bronze/` (extracted, per period)
- Immutable: never modified; file hashes tracked in `data/raw/manifest.csv` and `data/raw/ecb/`

### Silver (clean)
- Normalized parquet tables generated by PySpark, partitioned by `FechaDatos`:
  - `fund_nav_daily` — daily NAV, participants, patrimony (FONDMENS)
  - `fund_metadata` — fund name, manager, depositary, ISIN (FONDREGISTRO)
  - `fund_quarterly` — per class: AUM, participants, fees, official returns/volatility; per compartment: investor vocation; per entity: currency (FONDTRIM, semiannual 06/12)
  - `fund_holdings` — raw portfolio position lines per compartment (FONDCART, semiannual 06/12)
  - `fund_period_financials` — compartment-level expenses, income, net flow, net return, turnover and patrimony (FONDPATRIMDISVAR, cumulative YTD; downloaded archives contain 06/12)
  - `estr_daily` — ECB compounded €STR index and rate series (long table, keyed by `series`)
- Location: `data/silver/`
- Status: **built** for FONDMENS/FONDREGISTRO/FONDTRIM/FONDCART/FONDPATRIMDISVAR/€STR — 41 monthly periods (202301–202605), 6 semiannual holdings closures (202306–202512) and 6 financial periods (202306–202512).

### Gold (analytical)
- Business-ready models generated by dbt (dbt-duckdb), destination `data/gold/cnmv.duckdb`:
  - **Dimensions**: `dim_compartment`, `dim_class`, `dim_date` (single date table), `dim_manager_group`
  - **Facts**: `fact_nav_daily` (daily NAV/AUM/holders, `is_valid_nav`), `fact_fund_period_financials` (FONDPATRIMDISVAR YTD), `fact_fund_quarterly_metrics`, `fact_holdings` (all FONDCART periods; `position_rank <= 10` gives the top ten, and summing `weight` by `clase_if` the asset allocation), `fact_estr_weekly`
  - `mart_fund_panorama` — one row per active compartment through its representative class: metrics, AUM, participants, concentration, latest flows/fees, flags, watchlist status (`watchlist_status`, `rnk`; the selection lives in `int_fund_peer_ranking`)
  - `mart_fund_class_status` — one row per class: why it is or is not in the panorama (`in_panorama`, `not_representative`, `no_recent_nav`, `other_currency`, `short_history`, `quarantined`)
  - `fact_class_nav_weekly` — weekly NAV series rebased to 100, for charts
  - `fact_compartment_monthly` — AUM bridge, monthly flows and retention proxies (`is_flow_outlier`); fees are semiannual and live in `fact_fund_period_financials` (`is_fee_outlier`, annualized columns)
  - `fact_fund_anomalies` — typed anomaly list with severity, date key and source
  - `fact_market_fee_and_aum`, `fact_manager_group_monthly` — market and manager-group fee aggregates
- Status: **built** (dbt project exists; `dbt build` green on real data and on the CI fixture, no warnings)
- Silver entity names are the data-layer contract; Gold grains are documented in `dbt/models/**/**.yml`
- dbt documentation and lineage graph (static, one file): `docs/dbt_docs/index.html`. Regenerate with `cd dbt && dbt docs generate --static` and copy `target/static_index.html`.
- Local destination: `data/gold/cnmv.duckdb`. BI export: `python bi/export_gold.py` → `data/exports/gold_bi/*.parquet` + `_manifest.json`.
- Azure destination (Release 2): Azure SQL Database (Gold), with ADLS Gen2 for Bronze/Silver files

## Pipeline (monthly)

### Local (Release 1)

```
1. Download FONDMENS + FONDREGISTRO ZIPs (monthly) and FONDTRIM + FONDCART (months 06/12) + FONDPATRIMDISVAR (months 03/06/09/12); ECB €STR via Data Portal API
2. PySpark: parse XML/CSV → Silver parquet tables (spark/jobs/build_silver.py)
3. Quality gate: spark/jobs/validate_silver.py (FINDINGS contract)
4. dbt: staging (views) → intermediate (tables; the quality classification is a view) → `dimensions/`, `facts/` and `reports/` (tables) plus `meta/meta_run` (single source of the cut-off), rebuilt for the selected `as_of_period`
5. Power BI / SQL analysis on Gold
```

### Azure (Release 2)

```
1. Airflow DAG on Azure VM triggers ingestion
2. Bronze/Silver/Gold files in ADLS Gen2
3. PySpark local mode on the VM reads/writes ADLS with managed identity
4. Silver loaded into Azure SQL Database serverless
5. dbt-sqlserver builds Gold in Azure SQL
6. Power BI connects to Azure SQL
7. run_log + Log Analytics for observability
```

## Design Decisions

- **PySpark standalone**: selected for pedagogical purposes and ability to handle complex nested XML schemas locally without a cluster
- **DuckDB**: supports advanced SQL (window functions, CTEs) without a server
- **Full rebuild by `as_of_period`**: `meta_run` resolves the cut-off once (`latest` or an explicit `YYYYMM`) and every model reads it from there. The cut applies to all facts and dimensions, so a rebuild with an earlier cut contains no later data (checked with 202512; with data from 2023-01 the first cut with a complete 36-month window is 202512). Staging models are views; intermediate, dimension, fact and report models are tables rebuilt on each run. At the current data volume this is fast and keeps `dbt build` idempotent; incremental materializations can be introduced when volume or runtime justifies them
- **Provenance**: Bronze keeps source URL/file name, ingestion timestamp, period and file hash in `data/raw/manifest.csv`; each dbt run records `as_of_period` and the invocation in `dbt/target/` artifacts. A Gold row can be traced back to its Silver table and, through the period, to the source file
- **Exploration notebooks**: grouped by decision question, not one per source. `01` profiles NAV/metadata anomalies, `02` calibrates selection thresholds from the semiannual snapshots, and `03` validates the FONDPATRIMDISVAR financial contract. A source appears in more than one notebook only as supporting context, never as the object of study
- **Airflow**: added after local pipeline is working (Release 2), not before
- **Azure SQL over Synapse/Databricks**: the data volume does not justify a lakehouse; serverless SQL is enough and cheaper
- **ADLS Gen2 over local-only**: demonstrates cloud storage/auth without re-architecting the pipeline
- **Bicep over Terraform**: native Azure, smaller surface for a solo project
- **dbt-sqlserver risk**: compatibility with dbt-core 1.12.5 must be validated; fallback is Azure PostgreSQL + dbt-postgres
- **Solo project**: lightweight tools, no production infrastructure; Azure budget alert and auto-shutdown are mandatory
